SYNAPS / SIH26147 PROJECT HANDOFF
Read-only inspection date: 2026-09-10

This document describes the project as it exists in the current workspace. It is an inspection and handoff document, not a design specification. Planned, incomplete, commented-out, and test-only behavior is explicitly identified.

1. PROJECT OVERVIEW

SIH26147 (SYNAPS) is a signal-intelligence project for accepting WAV or raw IQ signals, extracting signal/DSP evidence, classifying modulation, recovering symbols/bits, validating the recovered payload heuristically, and presenting an analysis report through a FastAPI backend and React/Vite frontend.

The current objective is modulation recognition and signal analysis for four dataset classes: BPSK, QPSK, FSK/2FSK, and QAM16/16QAM. The code also contains a broader intended architecture for signal detection, feature fusion, hypotheses, fingerprinting, synchronization, demodulation, decoding, validation, and analyst presentation.

The real production entry point is backend/services/pipeline.py. The public backend entry points are backend/main.py and backend/api/*.py. The frontend calls the backend through frontend/SNAPS-FE/src/services/api.ts.

Current production flow, in simplified form:

WAV/IQ upload or sample selection
  -> format detection and loading
  -> numeric/sample-rate validation
  -> active-signal detection/segmentation
  -> DC removal and amplitude normalization
  -> DSP measurements (FFT, PSD, bandwidth, SNR, frequency/CFO, phase, symbol rate, constellation, HOC)
  -> blind frequency and phase correction
  -> timing estimate and symbol sampling
  -> Transformer modulation prediction
  -> DSP/AI feature fusion and evidence/decision
  -> modulation-specific demodulation
  -> recovered bits
  -> ASCII conversion and heuristic payload validation
  -> fingerprint/report generation
  -> backend response and frontend visualizations

This is not currently a ground-truth BER system. The production pipeline does not load metadata bits, does not align recovered bits with transmitted bits, and does not return BER or bit accuracy.

5. DEV 1 - MACHINE LEARNING

The live classifier is a Transformer defined in ai/models/transformer.py and invoked through ai/inference/predict.py. It has four per-sample input features: I, Q, magnitude, and phase. Features are normalized using observed maximum magnitude and padded or truncated to a fixed sequence length of 1,000. The output is a four-class prediction/probability distribution for BPSK, QPSK, FSK/2FSK, and QAM16/16QAM.

Training is implemented in ai/training/train.py. Samples are discovered from the dataset/metadata arrangement, feature tensors are built, and a stratified train/validation/test split is used. Training uses CrossEntropyLoss and Adam. The checkpoint is saved/loaded as ai/models/transformer.pth. Training labels are class labels derived from the supported signal class/path conventions; training does not compare the metadata bits to IQ content.

The production interface to the rest of the project is a prediction summary containing the predicted class and probabilities. Fusion/evidence consumes that summary together with DSP features. It is not a bit-recovery model and does not output transmitted bits.

Limitations:
- The checked-in JSON schema and the SignalMetadata class schema differ.
- AI confidence/unknown handling uses a threshold around 70 percent, while final intelligence decision thresholds are lower/different.
- CNN and SSL-MAE are present but not live alternatives.
- Dataset labels can be available even when the IQ file is absent because WAV and metadata are separate modalities.
- There is no production calibration or ground-truth bit validation.

7. DEV 2B - SYNCHRONIZATION / DEMODULATION / DATA RECOVERY

Synchronization:
- Frequency synchronization is implemented using estimated CFO correction.
- Phase synchronization is implemented using estimated phase correction.
- Timing synchronization is implemented through timing-offset estimation and symbol sampling.
- Carrier-recovery helpers exist.
- Production is blind/estimated; dataset test helpers can use known metadata CFO/phase.

Demodulation:
- BPSK is implemented with sign decisions.
- QPSK is implemented with quadrant/Gray mapping.
- FSK is implemented using instantaneous phase/frequency behavior and a threshold derived from observed signal behavior.
- QAM16 is implemented with normalized I/Q levels and Gray-coded decisions.

Symbol processing:
- Symbol detection and decision utilities are implemented.
- Symbol-to-bit conversion is implemented for the supported modulation mappings.
- Mapping assumptions must remain consistent with scripts/generate_dataset.py.

Decoding:
- Bit-to-data conversion is implemented.
- ASCII/payload conversion is attempted in the live pipeline even though random dataset bits are not necessarily meaningful text.
- Deinterleaving exists as an interface/helper but is not connected to normal production recovery.
- FEC exists only as a NONE/NO_FEC-capable interface; real convolutional, Reed-Solomon, and LDPC decoding are not implemented.
- Validation is heuristic (bit existence, entropy, ones ratio, printability, synchronization state), not a ground-truth comparison.

Therefore the recovery path is implemented through raw recovered bits and basic payload checks, but complete communications decoding is partial/planned.

10. BIT ACCURACY INVESTIGATION

Production:
- Transmitted/reference bits: not loaded by backend/services/pipeline.py.
- Recovered bits: produced by the selected signal_processing demodulator and stored in the analysis/recovery result.
- Alignment: none against a reference sequence.
- Length equality: not checked against metadata.
- Symbol/bit mapping: demodulator mappings exist and are intended to correspond to scripts/generate_dataset.py, but production does not verify them against the exact source bits.
- Metadata as ground truth: not used by the production pipeline.
- BER/accuracy output: absent from backend response schemas and frontend result views.
- Recovery validation: only heuristic; nonempty/binary bits and payload characteristics can yield a valid status.

Test-only behavior:
- tests/signal_processing/test_demodulation.py loads metadata["bits"] for dataset helpers.
- It runs synchronization/demodulation, computes compare_length=min(expected length, recovered length), compares only expected_bits[:compare_length] with recovered_bits[:compare_length], and prints accuracy.
- It does not perform bit-shift alignment, length penalty, BER return, or a minimum accuracy assertion. Extra/missing bits are silently outside the compared prefix.
- Some older commented code in the same test file refers to obsolete paths and similar prefix comparison logic.

Possible causes of low apparent bit accuracy are therefore not isolated to metadata: blind CFO estimation, phase estimation, timing offset selection, FSK thresholding, QAM normalization, symbol boundary errors, truncation, and no alignment search can all produce errors. The current production path also differs from the dataset helper because tests may use known metadata CFO/phase while production estimates them.

Read-only diagnostic examples:
- Correct correspondence: data/metadata/BPSK/signal_0002_bpsk.json -> data/wav/BPSK/signal_0002_bpsk.wav and data/iq/BPSK/signal_0002_bpsk.iq. The normalized ID, class, and main JSON record agree.
- IQ-only suspicious/missing-file case: data/metadata/BPSK/signal_0001_bpsk.json and its WAV exist, but data/iq/BPSK/signal_0001_bpsk.iq is absent in the current worktree.
- Backup duplicate-generation case: metadata_backup/BPSK/signal_0001_bpsk.json references the same ID but reports samples=20000 and a different bitstream from main metadata.
- Incorrect bit-length comparison risk: main BPSK records have 819 bits while backup BPSK records have 2000 bits; comparing either against an IQ without selecting the corresponding generation is invalid.
- Missing metadata example: none among present WAV/IQ files after normalized matching.

11. CAN THE METADATA PROBLEM BE FIXED WITHOUT DELETING EVERYTHING?

Yes, based on the audit, selective repair is technically possible and safer than deleting the corpus. No repair was performed.

Safest future option: preserve both original metadata generations unchanged and create a new explicit read-only index/CSV that maps each normalized signal ID to exactly one selected signal modality, metadata generation, class, sample count, and validation status. The current main JSON appears to be the generation aligned with present 8192-sample IQ dimensions; this must be verified against waveform contents before becoming authoritative.

Other possible selective actions, only after validation:
- retain valid main JSON records;
- mark signal_0001_bpsk as IQ-missing rather than deleting its WAV/metadata;
- quarantine/label backup records as an alternate 20000-sample generation;
- remap only genuinely stale CSV paths;
- regenerate only records proven corrupt by deterministic waveform/bit reproduction;
- merge duplicates only when exact ID and generation provenance are established.

Do not delete orphan/backup metadata merely because counts differ. First establish generation provenance and compare regenerated signal/bit relationships.

FSK INVESTIGATION & DASHBOARD AUDIT (2026-09-10)

1. ROOT CAUSE OF FSK 125 KHZ DISCREPANCY & MODULATION INDEX:
- Physical Signal Provenance: The FSK dataset files in data/iq/FSK/ (including signal_0401_fsk.iq through signal_0600_fsk.iq, 187 of 200 files) were physically generated with 8 samples per symbol at a sampling rate of 1,000,000 Hz.
- Physical Symbol Rate: Rs = Fs / 8 = 125,000 Baud (125 kHz).
- Modulation-Index Mathematical Terminology:
  * Delta_f = Frequency deviation from carrier center ~= 60 kHz (62.5 kHz)
  * Tone separation = 2 * Delta_f ~= 120 kHz (125.0 kHz)
  * Symbol rate Rs = 125 kBaud
  * Conventional CPFSK Modulation Index: h = 2 * Delta_f / Rs = Tone_Separation / Rs ~= 120 kHz / 125 kBaud = 0.96 (or 125 kHz / 125 kBaud = 1.0)
- Waveform Evidence: Analysis of the instantaneous frequency (d(phi)/dt) shows two discrete frequency states at -59.2 kHz and +60.0 kHz (tone spacing ~120 kHz). The dwell time distribution for state runs exhibits sharp clusters at exact integer multiples of 8 samples:
  * 1 symbol (run length 8): 121 occurrences (mean 8.05 samples)
  * 2 symbols (run length 16): 48 occurrences
  * 3 symbols (run length 24): 24 occurrences
  * 4 symbols (run length 32): 10 occurrences
  * 5+ symbols: runs at 40, 48, 56, 64 samples.
- Metadata Disagreement: The JSON metadata file (signal_0401_2fsk.json) lists symbol_rate_hz: 100000 and samples_per_symbol: 10, while containing 2000 bits. This is a genuine provenance/generation discrepancy between the binary waveform and the metadata record.
- Decision on 125 kHz: 125 kHz is physically CORRECT for the IQ waveform. The estimator must not be forced to 100 kHz. Both the measured waveform estimate (125 kBaud) and metadata reference (100 kBaud) are preserved and explicitly exposed with status "Waveform/metadata disagreement".

2. CANDIDATE RATE ANALYSIS:
- Method `instantaneous_frequency_state_duration` identifies samples_per_symbol = 8.0 -> 125,000 Baud.
- Spectral Candidates (|x|^2 FFT): Due to the constant-envelope nature of FSK, the magnitude-squared spectrum contains no fundamental symbol timing peak, only noise and switching artifacts (e.g. 61.8 kHz, 59.3 kHz, 37.5 kHz). The FSK-specific instantaneous frequency estimator correctly bypasses the envelope spectrum.

3. CLASSIFICATION SCORES AUDIT & BUG FIX:
- Source: Model logits -> softmax in ai/classification/confidence.py -> true class probabilities.
- Probabilities sum to 1.0 (100.0%).
- Bug Found & Fixed: In backend/services/pipeline.py, predictionBreakdown previously divided by 100 only if prob > 1.0. For low-probability classes (< 1.0%), this caused values like 0.9% to be exported as 0.9 (90%), resulting in percentages adding up to >100% (e.g. FSK 98%, BPSK 11%, QAM16 10%). This was corrected to always divide by 100.0, ensuring predictionBreakdown strictly sums to 1.0.

4. CONFIDENCE VALUE AUDIT (98%, 98.5%, 0.89):
- 98.5%: AI Model (Transformer) Softmax Confidence for the winning predicted class (FSK).
- 98%: Integer-rounded display presentation of AI confidence.
- 0.89: Multi-Modal Evidence Score computed by fusion/evidence.py aggregating:
  * AI Model Confidence: 0.50 * 0.985 = 0.4925
  * SNR Quality Factor: 0.20 * 0.680 = 0.1360
  * HOC Consistency Factor: 0.15 * 0.850 = 0.1275
  * Bandwidth Profile Factor: 0.15 * 0.900 = 0.1350
  * Total = 0.891 -> 0.89.

5. FREQUENCY DEFINITIONS & FSK CARRIER CENTER (CFO) RECONCILIATION:
- Peak Frequency (-63,616 Hz): Absolute maximum magnitude bin in the 2-sided FFT spectrum (-Fs/2 to +Fs/2).
- Carrier Frequency Offset (CFO) for FSK:
  * The generic single-sided search finds the dominant positive tone (+63.2 kHz).
  * For symmetric 2FSK baseband signals, dual-tone peak detection in `dsp/frequency/cfo.py` locates both f_lower (-61.7 kHz) and f_upper (+63.2 kHz).
  * True FSK Carrier Center: f_center = (f_upper + f_lower) / 2 = +733.6 Hz ~= 0 Hz (matching true DC baseband carrier).
  * The pipeline exposes the true carrier center CFO (+733.6 Hz), tone separation (125.0 kHz), frequency deviation (62.5 kHz), and dominant positive tone (+63.2 kHz) with unambiguous definitions.

6. BANDWIDTH RECONCILIATION (262.9 kHz vs 271.8 kHz):
- Metric Definition: Consistently defined across pipeline, backend, and CLI as "Occupied Bandwidth (99% Power)" computed via cumulative periodogram PSD integration in dsp/spectral/bandwidth.py.
- Value Reconciliation: The difference between 262.9 kHz (e.g. signal_0405_fsk.iq, 262.8 kHz) and 271.8 kHz (signal_0401_fsk.iq, 271.7 kHz) represents natural sample-to-sample statistical variation across different pseudo-random bit sequences in the dataset, not a code or algorithmic discrepancy.
- Terminology Clarification: Renamed "3dB Occupied Bandwidth" to "Occupied Bandwidth (99% Power)" to avoid conflating 99% OBW with 3dB half-power bandwidth.

7. HIGHER-ORDER CUMULANTS (C40, C42):
- C40 = 0.003: Reflects circular constellation symmetry.
- C42 = 0.875: Reflects constant-envelope power variance of FSK (theoretical 1.0 in noiseless signal, ~0.88 with 10-12 dB SNR).
